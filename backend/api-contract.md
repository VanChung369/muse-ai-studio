# Project API Contract

FastAPI's `/openapi.json` is the authoritative machine-readable contract. The checked-in `openapi.json` is an exported snapshot.

- `GET /api/projects`: HTTP 200 with one page of project summaries.
  - Query: `q` (name search, up to 100 characters; case-, accent-, and `đ`-insensitive; `%` and `_` are literal), `status` (`all` default, `inProgress`, `completed`, `cancelled`; `inProgress` is every status except `completed` and `cancelled`, so failed projects are included), `sort` (`updated` default: newest update first; `name`: A–Z by the normalized name; `duration`: longest first, then newest update), `limit` (1–100, default 24), and `cursor`.
  - Response: `{ "items": [...], "total": 0, "nextCursor": null, "counts": { "all": 0, "inProgress": 0, "completed": 0, "cancelled": 0 }, "featured": null }`.
  - `items` are card summaries with identity, status, aspect ratio, target duration, timestamps, scene counts, and cover tone. Fetch the detail endpoint for the idea, shared script descriptions, revision, and full scenes.
  - `total` counts projects matching `q` and `status` across all pages. `counts` (status chips) and `featured` ignore `q` and `status`. `featured` is the most recently updated `ready` project, otherwise the most recently updated in-progress project, and includes up to six `previewScenes` (`number`, `title`).
  - Pagination is keyset-based: pass `nextCursor` back as `cursor` with the same `q`, `status`, and `sort` until it is `null`. Each order ends with the project ID, so projects created between requests never cause later pages to repeat or skip rows. Cursors are opaque; a malformed cursor or one issued for another `sort` returns HTTP 400 with `detail.code = invalid_cursor`. Invalid `status`, `sort`, or `limit` values return HTTP 422.
- `POST /api/projects`: HTTP 201 and a `Location` header. Required `name` is trimmed, 1–100 characters. Optional `idea` defaults to an empty string and has a 12,000-character limit. `durationSeconds` defaults to 60 and must be an integer from 10–3,600 (one hour), divisible by 5. Nothing stops a long film; the app only warns past 300 seconds, because every scene is a generation on Muse. `aspectRatio` defaults to `16:9`; allowed values are `16:9`, `9:16`, `1:1`, `4:3`, `3:4`, `4:5` and `21:9`. Unknown fields are rejected with HTTP 422.
- `GET /api/projects/{project_id}`: HTTP 200 for a saved project; HTTP 404 with `detail.code = project_not_found` otherwise. Treat IDs as opaque strings.

Responses use camelCase fields matching the frontend project schemas. Dates are UTC ISO 8601 strings ending in `Z`. New projects are drafts with zero scenes, zero completed scenes, and an empty scene list. Script generation is a separate background operation; creating a draft does not contact Muse. Video rendering is not implemented yet.

SQLite persists projects across service restarts. No sample projects are inserted automatically, and browser-local demo drafts are not silently imported or deleted. The development service is accessed through the Vite `/api` proxy. Access-key setup belongs to a later application step; these initial local-development endpoints do not implement authentication yet.

POST is not idempotent. The frontend does not automatically retry failed create requests and keeps form values so users can decide whether to retry. List and detail failures have separate retry controls; transport errors must not appear as an empty collection or a missing project.

## Script editing

`PUT /api/projects/{project_id}/script` atomically replaces a project's script. Only `draft` and `ready` projects can be edited. Request fields are `expectedRevision` (nonnegative integer), `characterBible` (optional, up to 10,000 characters), `visualStyle` (optional, up to 3,000 characters), and `scenes` (1–720: an hour of 5-second scenes). Scenes are numbered consecutively from 1; each has a trimmed `title` (1–300), `prompt` (1–6,000), `durationSeconds` (5 or 10), and optional `narration` (up to 600). Scene durations must add up to the project's target duration.

A successful save returns the full project with HTTP 200, increments `scriptRevision`, updates `updatedAt`, and sets status to `ready`. This status means the script is available for review; it does not start rendering. Full project responses include `characterBible`, `visualStyle`, `scriptRevision`, and the persisted scenes. List summaries include the real scene count and featured projects include up to six scene titles.

HTTP 404 means the project does not exist. HTTP 409 uses `detail.code` of `script_conflict` when the revision is stale, or `script_locked` when the project status prevents editing. HTTP 422 covers invalid input and uses `script_duration_mismatch` for a total duration mismatch. Validation/conflict failures leave the previous script unchanged. The revision is checked by the database update so concurrent editors cannot silently overwrite each other. A fresh draft has revision 0 and no script. The editor builds an empty scene outline locally; it does not generate AI content or contact Muse.

## Project deletion

`DELETE /api/projects/{project_id}` returns HTTP 204 with an empty body after deleting the project and its script scenes in one transaction. Other projects remain unchanged. Unknown IDs return HTTP 404 with `detail.code = project_not_found`. Projects in `planning`, `rendering`, or `cancelling` return HTTP 409 with `detail.code = project_busy` and remain unchanged; stop the running operation before deleting. The status check is part of the database delete, so a project cannot be removed after a concurrent operation starts.

The UI requires confirmation naming the project. Failed requests retain the confirmation dialog with a retry action. HTTP 404 is treated as successful removal in the UI, including when another tab already deleted the project. Successful deletion closes its detail sheet, clears its selected URL parameter, removes its detail cache, and refreshes paginated lists and counts from the first page. No request is sent merely by opening or cancelling the dialog.

## Muse account management

These endpoints manage imported sessions locally. They do not contact Muse, verify authentication, read quota, or make imported accounts eligible for generation yet. Every account has `sessionStatus: "unverified"`; `enabled` is an independent preference.

- `GET /api/accounts`: HTTP 200, `{ "items": [...], "total": 0 }`, newest created first, ID breaks ties. Updating, checking, or enabling an account never changes its position.
- `POST /api/accounts`: HTTP 201 and `Location`. Required `label` is trimmed, 1–100 characters. Required write-only `cookieText` is 1–1,048,576 characters (enough for a full browser export). Parsing is lenient so users can paste whatever they copied: a Cookie header (optional `Cookie:` prefix, line breaks allowed, quoted `document.cookie` output), a raw DevTools request-header block, "Copy as cURL" (`-H 'cookie: …'`, `-b`/`--cookie`), "Copy as fetch", a flat JSON name/value object, a browser-extension JSON array (any number of sites), Playwright/Puppeteer storage state (`{"cookies": [...]}`), Netscape `cookies.txt`, or tab-separated rows copied from the DevTools cookie table. Cookies for other domains, Set-Cookie attributes (`Path`, `HttpOnly`, …), stray lines, and invalid names or values (non-ASCII, spaces, controls, over 8,192 characters) are skipped rather than failing the import. For duplicate names, the cookie whose domain is `muse.ai` itself wins, otherwise the first one. Expiry is read from JSON exports, `cookies.txt`, and DevTools rows. Only two cases fail: no cookie could be read (`invalid_cookies`) or no nonempty `hatch_sess` was found (`missing_session`). At most 100 cookies are kept (always including `hatch_sess`); presence alone does not establish validity.
- `GET /api/accounts/{account_id}`: HTTP 200 public metadata or HTTP 404, `detail.code = account_not_found`.
- `PATCH /api/accounts/{account_id}`: change `label` and/or strict boolean `enabled`; at least one field is required. Returns HTTP 200 public metadata or HTTP 404. Cookie replacement is not supported yet.
- `DELETE /api/accounts/{account_id}`: HTTP 204, empty body, or HTTP 404.

Public account metadata contains only `id`, `label`, `enabled`, `cookieCount`, `sessionStatus`, `createdAt`, and `updatedAt`. Cookie values, encryption data, and session fingerprints are never returned, including in validation errors. Every `/api/accounts` response, including errors, sends `Cache-Control: no-store`. Unknown fields and invalid request shapes return HTTP 422. Cookie parsing errors use HTTP 422 and `detail.code = invalid_cookies`; missing `hatch_sess` uses `missing_session`. Duplicate imports of the same session return HTTP 409 and `account_exists`, even if cookie order or other cookie values differ. The UI keeps failed import input in memory for correction, resets it on close/success, and never stores credentials in browser storage or the query cache.

Cookies are encrypted using Fernet before insertion. A random encryption key is created automatically at `data/account-secret.key` with file mode 0600. Backups that need to restore accounts must preserve both the SQLite database and this key. Startup refuses to replace a missing key when encrypted accounts exist, or to open those accounts with a different key. The key is published atomically with a hard link; on filesystems without hard links (FAT/exFAT, SMB, some container mounts) it falls back to an exclusive create. Duplicate detection uses an HMAC of `hatch_sess` keyed with an HKDF subkey of this key (separate from encryption); startup recomputes any fingerprint written with an older derivation. Importing the Python app alone creates neither database nor key. Runtime data stays ignored by Git.

## Extended account data and operations

Account responses now include `sessionStatus` (`unverified`, `valid`, `invalid`), `expiresAt` (actual imported/returned cookie expiry, null when unknown), `quota` (nullable sanitized usage data), `quotaCheckedAt`, `lastUsedAt` (generation use only, null until generation integration), `lastCheckedAt`, `lastKeepaliveAt`, `notes`, `lastError`, `proxy` (server, username, hasPassword; never password), and `credentialVersion`.

`PATCH /accounts/{id}` also accepts `notes` (up to 2,000 characters). `PUT /accounts/{id}/cookies` accepts write-only `cookieText`, preserves the account ID/label/preferences/notes, replaces credentials, reads cookie expiry metadata from browser JSON, clears previous health/quota, and rejects a session already attached to another account. `PUT /accounts/{id}/proxy` accepts `proxy: null` (direct) or `{server, username, password?}`. HTTP, SOCKS5, and SOCKS5H origins are supported; proxy usernames and passwords must be Latin-1 (proxies receive them as Latin-1 bytes), otherwise HTTP 422; an omitted password preserves the saved password only when origin and username are unchanged. Changing the route invalidates previous health/quota data. Proxy credentials are encrypted.

`POST /accounts/{id}/test`, `/keep-alive`, and `/quota` perform real upstream operations through the saved route. Test reads `/api/session` and requires an assigned session. Keep alive additionally requests VM wake and verifies its state; acknowledgment alone does not confirm the VM is running. Quota opens an isolated Chromium context and reads the existing Muse Settings usage panel. Successful operations return `{account, code, ok, vmState}`. Authentication failure marks the session invalid and returns `ok: false`; network/403/rate-limit/parser failures preserve previous health/quota and return a sanitized HTTP 502/504 detail code. No upstream response body or request credentials are exposed. Each account permits one credential/proxy/delete/upstream operation at a time (HTTP 409 `account_busy`); revision checks prevent results overwriting credentials changed by another process.

Quota means provider-reported weekly usage percentage, plan, reset text and optional additional-token usage; it is not a fabricated remaining-video count. Unknown values remain null. Session test and maintenance do not update `lastUsedAt`. Quota requires an installed Chromium/Chrome executable (auto-detected, or `MUSE_BROWSER_PATH`); no external engine service is required. The default upstream is `https://muse.ai`; a loopback-only test origin can be supplied by `MUSE_UPSTREAM_URL` for simulation. The legacy web-session protocol and quota selectors come from the reference repository, not a published provider API contract.

Remote operations (`test`, `keep-alive`, `quota`) persist cookies Muse rotates in any successful response, even when a later step of the same operation fails (for example the workspace is not assigned, or the quota browser step fails). If the rotated cookies no longer contain `hatch_sess`, the previous credentials are kept and the account is marked `invalid`. A saved proxy that cannot be used reports `proxy_error` instead of failing with HTTP 500.

## AI script proposals

`POST /api/projects/{project_id}/script-generation` accepts `{accountId, idea, expectedRevision}` and returns HTTP 202 with a task response. The idea is trimmed and must be 1–12,000 characters. The selected account must exist, be enabled, and have a verified session. The project must be draft/ready with the expected saved-script revision. The operation saves the brief and queues one `plan_script` task atomically. A second active generation for the same project returns HTTP 409 `generation_active`; invalid accounts return `account_unavailable`, missing projects 404, and changed/locked scripts 409 `script_conflict`.

The task uses the shared account lock, saved encrypted cookies/proxy, and an isolated browser. Refreshed session cookies are persisted before submission. `submittedAt` is marked before the send click; a restart after this point interrupts the task rather than silently sending again. This handler has one attempt and never automatically resends an uncertain request. Cancellation closes the current browser attempt; it does not claim that an already sent upstream request was undone.

Muse must return a complete JSON script with the exact target timeline (10-second scenes, then a final 5-second scene if needed). The parser validates numbering, duration, text limits and schema without inventing missing output. A successful task stores `{projectId, script}` in its result; `script` includes the original `expectedRevision`. This proposal does **not** replace the saved script or change its revision. The UI previews the scenes and applies them only through the existing `PUT /projects/{id}/script`, preserving conflict protection. A failed, cancelled or interrupted generation preserves the previous saved script.

`GET /api/projects/{project_id}/script-generation` returns the latest planning task or null; unknown projects return 404. Task state and proposals persist across reloads. While a planning task is queued/running, project deletion returns 409. The UI polls active tasks, supports stopping them, and warns that a new attempt can consume additional quota. There is no video rendering in this operation.

## Project settings

`PATCH /api/projects/{project_id}` changes any of `name`, `idea`, `aspectRatio`, `durationSeconds`, `look`, `continuity`; only the fields sent are changed, and null is rejected. The first four can change while the project is `draft` or `ready`; after a render has started they return 409 `project_locked`. `look` (`auto`, `realistic`, `cinematic`, `documentary`, `commercial`, `animation3d`, `anime`) and `continuity` (`off`, `reference`, `seamless`) can change whenever no render is running (409 `project_busy` otherwise), so they also apply to a later "render again". A saved script adds up to the current duration: a different `durationSeconds` returns 409 `duration_locked` unless `discardScript: true` is sent, which deletes the script and returns the project to `draft`.

Projects also carry `language` (`auto`, `vi`, `en`, `zh`, `ja`, `ko`, `es`, `fr`, `de`, `pt`, `th`, `id`): the language of scene titles, narration and anything spoken. It is a render option like `look`. So is `mute` (boolean): a muted project asks Muse for silent scenes (narration and language are then left out of the prompt) and its merged video has no audio track. Changing `mute` on a `completed` project merges the video again from the existing clips (status `rendering` until done); no scene is rendered again. Project summaries include `coverUrl`, a still of the first rendered scene (null until one exists).

`POST /api/projects/{project_id}/script-generation` additionally accepts `language` and `look` (saved on the project), `narration` (write a voice-over line for every scene) and `direction` (up to 2,000 characters of free-form direction for the writer).

## Project brief and reference material

`POST /api/projects` and `PATCH /api/projects/{project_id}` also accept `characterBible` (up to 10,000 characters), `visualStyle` (3,000) and `music` (500): optional starting points that reach the script writer and every scene prompt. `characterBible` and `visualStyle` belong to the script, so they are fixed once a render has started and changing them bumps `scriptRevision`; `music` is a render option.

`GET /api/projects/{project_id}/references` lists a project's reference files (also returned as `references` on the project): pictures (PNG, JPEG, WebP, GIF) and videos (MP4, WebM, MOV) showing the characters, products, places or look to keep. `POST /api/projects/{project_id}/references?name=<file name>` uploads one file as the raw request body with its type in `Content-Type` (201; 415 `unsupported_file`, 413 `file_too_large` above 50 MB, 409 `too_many_files` above 6, 409 `project_busy` while rendering). `GET .../references/{reference_id}` serves it and `DELETE` removes it. Reference files are attached to the first message of the project's Muse conversation (the script request or scene 1) and again whenever a new conversation is started. Adding or removing a file makes the project's next message start a new conversation, so Muse sees the current set of files. The file is served with the uploaded type and `X-Content-Type-Options: nosniff`.

`GET /api/projects/{project_id}/scenes.zip` downloads every rendered scene clip in one archive.

## Media added to a film

`GET /api/projects/{project_id}/media` lists the files the user added to a film from outside its script, oldest first: `{id, kind, name, mime, size, seconds, width, height, source, url, thumbnailUrl}`. `kind` is `video`, `image` or `audio`; `seconds` is null for a picture, the frame size is null for audio, and `thumbnailUrl` is null for audio. An audio file also has `waveformUrl` (null for the other kinds): its sound drawn as a wide, see-through PNG, made the first time it is asked for (404 when FFmpeg cannot draw it). `source` is `upload`, or `muse` for music Muse generated.

`POST /api/projects/{project_id}/media?name=<file name>` uploads one file as the raw request body with its type in `Content-Type` (201). Accepted: MP4, WebM and MOV video; PNG, JPEG and WebP pictures; MP3, WAV, M4A/AAC and OGG audio. The file is read with FFmpeg to get its length and frame size, so the bytes must really be what the type says. Errors: 415 `unsupported_file`, 413 `file_too_large` above 200 MB, 422 `empty_file` or `unreadable_file`, 409 `too_many_files` above 30, 409 `project_busy` while rendering or merging, 409 `ffmpeg_unavailable`. `GET .../media/{media_id}` serves the file (with `X-Content-Type-Options: nosniff`), `GET .../media/{media_id}/thumbnail` a still of a video or picture, and `DELETE .../media/{media_id}` removes it (204; 409 `media_in_use` while the saved timeline places it in the film, 409 `project_busy`). Deleting the project deletes its media.

`POST /api/projects/{project_id}/media/music` with `{description}` (1 to 500 characters) asks Muse for background music (HTTP 202, a `generate_music` task). Muse makes videos, not audio files, so a 10-second clip is requested in a conversation of its own whose soundtrack is the music described; only that soundtrack is kept, as an audio file with `source: "muse"` among the project's media. One request runs per project at a time (409 `generation_active`); 409 `account_unavailable` without an enabled, verified account; 409 `too_many_files`. The task fails with `music_missing` when the clip has no sound and `ffmpeg_unavailable` without FFmpeg (checked before any quota is spent). `GET .../media/music` returns the latest such task, or null.

## Media library

The library is one list of everything made in Video Studio (each rendered scene clip and each finished film, which stay in their project) and of files uploaded to the library itself, which belong to no project.

`GET /api/library` returns `{items, total, counts}`, newest first. Optional query: `kind` (`image`, `video`, `audio`), `source` (`studio` for scenes and films, `upload`), `q` (matched against the title and the project's name, ignoring case and accents), `limit` (default 60, at most 200) and `offset`. `total` counts what matches all three filters; `counts` is `{all, image, video, audio}` for the source and search alone, for filter chips. An item is `{id, role, kind, source, title, projectId, projectName, sceneNumber, assetId, seconds, size, url, thumbnailUrl, waveformUrl, createdAt, deletable}`: `id` is `upload:<asset id>`, `scene:<project id>:<number>` or `film:<project id>`; `role` is `upload`, `scene` or `film`; `title` is the file's name, the scene's title, or the project's name for a film; `seconds` is null for a picture and for a film; `deletable` is true only for uploads. Entries whose file is missing from disk are left out.

`POST /api/library?name=<file name>` uploads one file as the raw request body with its type in `Content-Type` (201, the new item). It accepts the same types and sizes as a project's media and fails the same way: 415 `unsupported_file`, 413 `file_too_large` above 200 MB, 422 `empty_file` or `unreadable_file`, 409 `ffmpeg_unavailable`, and 409 `too_many_files` above 500 files. `GET /api/library/assets/{asset_id}/file` serves an uploaded file (`?download=true` to save it under its name), `.../thumbnail` a still of a video or picture, `.../waveform` the drawn sound of an audio file, and `DELETE /api/library/assets/{asset_id}` removes it (204; 404 `library_item_not_found`). Scenes and films are served by their project's routes and cannot be deleted here.

`GET /api/library/archive?ids=<id>&ids=<id>` downloads the chosen items (up to 100) as one zip, each under a name of its own; ids that do not exist are skipped, and 404 `library_item_not_found` is returned when none do.

`POST /api/projects/{project_id}/media/import` with `{ids}` (1 to 20 library item ids) copies those files into the project's media and returns the new media objects (201). The project gets copies of its own, so deleting the original later does not affect it. It is all or nothing: 404 `library_item_not_found` when any id is unknown, 409 `too_many_files` when the project would hold more than 30 files, 409 `project_busy` while rendering or merging, and 409 `ffmpeg_unavailable` when a scene or film has to be measured without FFmpeg.

## API keys and the public API

The trusted local UI manages keys without authentication. `GET /api/api-keys` returns active keys newest first as `{id, name, masked, createdAt, lastUsedAt}`. `masked` is `sk-muse-…` and the last four characters; timestamps are UTC, and `lastUsedAt` starts as null. `POST /api/api-keys` takes `{name}` (trimmed, 1–60 characters) and returns that object plus `key` (201). A key is `sk-muse-` followed by 48 lowercase hex characters. Only its SHA-256 hash and vault-encrypted ciphertext are stored. There may be 20 active keys (409 `too_many_keys`); invalid names return 422. `POST /api/api-keys/{id}/reveal` returns `{key}` (200). `DELETE /api/api-keys/{id}` revokes it permanently (204). Missing or revoked keys return 404 `api_key_not_found` for reveal and delete. These routes use the internal `{detail: {code, message}}` errors.

All `/v1` routes require `Authorization: Bearer <key>`. Missing, malformed, unknown and revoked keys return 401. Using a key updates `lastUsedAt` at most once a minute. Keys share the same accounts, quota and media library; a key can read a video generation made by another key.

`GET /v1/models` returns `{object: "list", data: [...]}` with models `muse-image` and `muse-video`; each entry has `{id, object: "model", created: 1763078400, owned_by: "muse"}`.

`POST /v1/images/generations` takes `{prompt, model?, n?, size?, aspect_ratio?, response_format?}`. The trimmed prompt is 1–4000 characters; `model` defaults to and must be `muse-image`; `n` is an integer 1–4 (default 1). `size` chooses a shape: `1024x1024` means 1:1 (default), `1792x1024` and `1536x1024` mean 16:9, and `1024x1792` and `1024x1536` mean 9:16. Instead, `aspect_ratio` may be `1:1`, `16:9` or `9:16`. Muse chooses the actual pixel size. `response_format` is `url` (default) or `b64_json`. Extra fields are ignored. The response waits for completion and returns `{created, data: [{url}]}` (200), or `{b64_json}` items containing the saved file bytes. URLs use the request's scheme and host and point to `/api/library/assets/{id}/file`, downloadable without a key. `X-Muse-Task-Id` identifies the background task, including on timeout.

`POST /v1/videos/generations` takes `{prompt, model?, aspect_ratio?}`. `model` defaults to and must be `muse-video`; `aspect_ratio` is `16:9` (default), `9:16` or `1:1`; prompt rules are the same as images. It queues one short video (about 10 seconds) and returns `{id, object: "video.generation", status: "queued", created, model: "muse-video"}` immediately (202). `GET /v1/videos/generations/{id}` returns the same fields with the current status: `queued`, `in_progress`, `succeeded`, `failed` or `cancelled`. Only success includes `data: [{url}]`; failure includes `error: {message, type, code}`. An interrupted task is reported as failed. Unknown ids, non-API tasks and image tasks return 404 `not_found`.

`POST /v1/chat/completions` takes `{model, messages, stream?}`, with `model` either `muse-image` or `muse-video`. It uses the last user message: string content, or the text parts of array content joined by newlines (other parts ignored). Missing or empty user text returns 400. It waits for the result and returns `{id: "chatcmpl-<task id>", object: "chat.completion", created, model, choices: [{index: 0, message: {role: "assistant", content}, finish_reason: "stop"}], usage: {prompt_tokens: 0, completion_tokens: 0, total_tokens: 0}}`. Content is `![image](<url>)` for pictures or `[video](<url>)` for a video.

With `stream: true`, chat returns `text/event-stream`. Each `data:` chunk has `object: "chat.completion.chunk"` and the same id, created and model. It starts with `delta: {role: "assistant"}`, sends `: waiting` comments about every 10 seconds, then `delta: {content}`, then an empty delta with `finish_reason: "stop"`, and ends with `data: [DONE]`. If work fails after streaming starts, its error message is sent as content and the stream finishes normally.

Generation uses the normal Quick Create background queue and appears in Tasks. Payloads carry `source: "api"`, `hidden: 1` and `apiKeyId`; outputs have library source `api` and are listed by `GET /api/library?source=api`. API work is absent from Quick Create history. Waiting releases database transactions between polls and gives up after the configured render timeout plus 120 seconds; the task may still finish.

All public errors have `{error: {message, type, code}}`, including validation errors (400 rather than 422) and unknown paths. Error mappings:

| HTTP | type                  | code                     | Cause                                                      |
| ---- | --------------------- | ------------------------ | ---------------------------------------------------------- |
| 401  | invalid_request_error | invalid_api_key          | Missing, malformed, unknown or revoked key                 |
| 400  | invalid_request_error | invalid_request          | Invalid body, model, prompt, shape or count                |
| 400  | invalid_request_error | content_policy_violation | generation_refused                                         |
| 404  | invalid_request_error | not_found                | Unknown video generation or path                           |
| 409  | invalid_request_error | library_full             | too_many_files                                             |
| 429  | rate_limit_error      | rate_limit_exceeded      | quota_exhausted or rate_limited                            |
| 502  | api_error             | upstream_error           | Other generation failures, cancellation or interruption    |
| 503  | api_error             | no_account_available     | account_unavailable, account_deleted or ffmpeg_unavailable |
| 504  | api_error             | timeout                  | generation_timeout or the waiting deadline                 |

## Quick Create

`POST /api/quick-create` accepts `{kind, prompt, aspectRatio, count, referenceAssetId}` and returns a batch (202). `kind` is `image` or `video`; `prompt` is trimmed, nonblank, and at most 4000 characters; `aspectRatio` is `16:9`, `9:16`, or `1:1`; `count` is an integer from 1 to 100 for images and exactly 1 for video. Videos request approximately 10 seconds, subject to Muse's output. `referenceAssetId` optionally points to an image in the library, attached as a visual reference or starting frame.

Each request is one persisted `generate_image` or `generate_video` task using automatic account selection. An image request sends one prompt asking for the complete image count as separate attachments in one Muse conversation. Selected reference bytes are attached before sending, including when continuing the same conversation. Outputs are saved as they arrive in the library with `source: quick`; existing library file, thumbnail, archive, import and deletion routes work for these outputs. The task checkpoints its conversation, account and saved asset ids. A manual retry uses that same conversation and account and asks only for missing outputs. If the original conversation cannot be opened, or a sent request's thread id is unknown, it fails with `conversation_unavailable` instead of silently opening another chat. No generation is automatically resent after an uncertain interruption.

`GET /api/quick-create?limit=20` returns the latest batches (up to 30). Each is `{id, kind, prompt, aspectRatio, count, completedCount, createdAt, tasks, items}`. New batches contain one normal task response; older batches with multiple tasks remain readable. `items` includes saved outputs even while the task is running or after a partial failure. `completedCount` counts all saved outputs, including files subsequently deleted from the library. Creation errors: 409 `account_unavailable`, `ffmpeg_unavailable` or `too_many_files`; 422 `reference_missing` or invalid request fields. Pending tasks reserve capacity for all images still missing. `image_count_mismatch` signals that Muse returned fewer outputs than requested; received files are preserved.

`DELETE /api/quick-create/{batch_id}` removes the entire request card from recent Quick Create results (204). It persists a hidden flag on all tasks in that batch, including older batches with one task per image; task records and library files are kept, and active tasks continue. `POST /api/quick-create/{batch_id}/restore` restores the card (204). Both return 404 `quick_create_not_found` for an unknown batch. Repeated removal is idempotent.

## Timeline

`GET /api/projects/{project_id}/timeline` returns the film's edit: `{projectId, status, editable, items, audio, volume, duck, captions, burnCaptions, captionStyle, titles, logo, output, canBurnCaptions, totalSeconds}`.

- `items` is the film's picture in play order. Each has `key` (names the entry while it is edited), `kind` (`scene`, or `video`/`image` for a file the user added), `scene` or `mediaId`, `title`, `clipSeconds` (the clip's real length; 30 for a picture, the longest it may be shown), `start` and `end` (the part that is kept, in seconds into the clip; for a picture `end` is how long it is shown), `enabled`, `speed` (2 plays twice as fast, so the piece takes half as long), `videoUrl` (null for a picture) and `thumbnailUrl`. Only scenes that have a clip are listed. A scene cut in two appears twice, each piece with its own `key` and part of the clip. Each piece also has a look: `effect` (`none`, `mono`, `sepia`, `warm`, `cool`, `vivid`, `vintage`, `blur`, `vignette`), `zoom` (`none`, or a slow push `in` / pull `out` over its length), `flip` (mirrored left to right), and `fadeIn` / `fadeOut` (seconds, up to 2, coming up from black and going to black; the piece's own sound fades with it).
- `audio` is audio laid over the film: `{key, mediaId, name, clipSeconds, waveformUrl, offset, start, end, volume, loop, fadeIn, fadeOut, url}`. `offset` is where in the film it starts, `start`/`end` the part of the file used, `loop` repeats that part until the film ends, and the fades are in seconds (up to 10). Audio always stops where the film ends, with a short fade when it is cut off and no fade out was set.
- `volume` is the volume of the sound the clips came with (1 = unchanged, 0 to 2). The project's `mute` option removes that sound altogether; audio laid over the film still plays. With `duck`, added audio is lowered while the clips' own sound is heard.
- `captions` are `{start, end, text}` in seconds into the film. With `burnCaptions` they are drawn into the picture when merging; without it they are only stored (the editor offers them as an `.srt` file). `captionStyle` is how they are drawn: `{size, color, outline, position, bold, box, font}` with `size` one of `small`, `medium`, `large`, `xlarge` (letters 4.5%, 6%, 8% or 10.5% of the frame's height), `color` and `outline` as `#RRGGBB`, `position` one of `bottom`, `middle`, `top`, `box` drawing a dark box behind the words instead of an outline, and `font` one of `Arial`, `Tahoma`, `Verdana`, `Times New Roman`, `Georgia`, `Courier New` (a font the server does not have falls back to its default). The default is medium white Arial with a black outline at the bottom.
- `titles` are words placed on the picture for a while: `{start, end, text, size, color, position, bold, box}`, with `position` one of nine places (`top-left`, `top`, `top-right`, `left`, `center`, `right`, `bottom-left`, `bottom`, `bottom-right`). They are always drawn.
- `logo` is a picture of the project kept in a corner for the whole film, or null: `{mediaId, corner, size, opacity, url}` with `corner` one of `top-left`, `top-right`, `bottom-left`, `bottom-right`, `size` its width as a percentage of the frame's width (5 to 40) and `opacity` 0.1 to 1.
- `output` is the shape and weight of the merged file: `{aspect, fit, height, quality}`. `aspect` is `source` (the shape of the scenes), `16:9`, `9:16` or `1:1`; in another shape `fit` shows the whole picture with bars (`contain`) or fills the frame and crops the edges (`cover`); `height` is the frame's shorter edge in pixels (0 keeps that of the scenes, or 480, 720, 1080); `quality` is `high`, `medium` or `small`.
- `canBurnCaptions` is false when the server's FFmpeg has no caption renderer (libass), which captions drawn into the picture and titles both need. `editable` is true while the project is `completed`; `totalSeconds` is the length of the film this edit makes.

`PUT /api/projects/{project_id}/timeline` replaces the edit and merges the film again from what it already has; no scene is rendered again. The body is `{items, audio?, volume?, duck?, captions?, burnCaptions?, captionStyle?, titles?, logo?, output?}`, where an item is `{scene | mediaId, key?, start, end, enabled?, speed?, effect?, zoom?, flip?, fadeIn?, fadeOut?}`, an audio entry `{mediaId, key?, offset?, start?, end, volume?, loop?, fadeIn?, fadeOut?}`, a caption `{start, end, text}`, a title as above and a logo `{mediaId, corner?, size?, opacity?}`. Rules (422 `invalid_timeline`, or 422 from validation): every rendered scene is listed at least once (more than once when it is cut into pieces) and no other scene; keys are unique; an item's `mediaId` must be a video or picture of this project, an audio entry's an audio file and the logo's a picture; each piece keeps at least 0.5 seconds inside its file; at least one item stays enabled; `speed` is 0.25 to 4 (always 1 for a picture); a picture is shown for at most 30 seconds; a caption or title stays for at least 0.2 seconds and holds at most 300 characters; at most 1,000 items, 8 audio entries, 1,000 captions and 50 titles. A film of more than 24 pieces is built in runs of 24 and then joined, so the picture is encoded twice. Captions and titles without text are dropped. It returns 409 `timeline_locked` unless the project is `completed` (also when it stops being so while the request is handled), 409 `ffmpeg_unavailable` without FFmpeg, and 409 `captions_unavailable` when captions or titles are to be drawn but FFmpeg cannot draw them.

`POST /api/projects/{project_id}/timeline/preview` takes the same body, saves nothing, and builds a small, quick, rough version of the film that edit would make (the shorter edge of the frame at most 360 pixels). It returns `{url, seconds}`; `url` is `GET .../timeline/preview.mp4` with a version, and each preview replaces the last. It fails like the PUT for an edit that does not fit, with 409 `scene_missing` / `media_missing` / `timeline_empty` when the film cannot be built, 409 `preview_busy` while another preview of the project is being made, and 422 `preview_failed` when FFmpeg fails.

A film that is only its scenes as they were rendered, at their own volume and frame, is joined without re-encoding when nothing is trimmed. Anything else (a trim, an added video or picture, a speed, a look or fade, audio, a changed volume, drawn captions, titles, a logo, another shape, size or quality) re-encodes the film. Its frame is that of its scenes unless `output` says otherwise; other shapes are fitted into it. A cut made on a clip that is later rendered again and comes out shorter is fitted to the new clip. The merge task fails with `media_missing` when a placed file is gone from disk.

`POST /api/projects/{project_id}/cover` with `{seconds}` uses the finished film's frame at that time as the project's cover (204; 404 without a finished film, 409 `ffmpeg_unavailable`, 422 `cover_failed` when there is no frame there), and `DELETE .../cover` goes back to the automatic cover (a still of the first rendered scene). A chosen cover is served with `Cache-Control: no-cache`.

## Rendering

`POST /api/projects/{project_id}/render` (HTTP 202) queues one `render_scene` task per scene, chained in order, and a final `merge_video` task. The project must be `ready` with at least one scene, and at least one enabled account must have a verified session (accounts are picked automatically, least recently used first). Otherwise it returns 409 `render_not_ready` or `account_unavailable`; nothing is queued. Starting a render sets the project to `rendering`, which locks its script.

`GET /api/projects/{project_id}/render` returns `{projectId, status, sceneCount, completedScenes, scenes, merge, videoUrl, usableAccounts}`. Each scene has `number`, `title`, `durationSeconds`, `videoUrl` (null until its clip exists) and `task` (its render task, null before a render starts). `merge` is the merge task. Poll it while the status is `rendering` or `cancelling`.

`POST /api/projects/{project_id}/render/cancel` cancels waiting tasks immediately and the running one after its current step; finished scenes are kept. `POST /api/projects/{project_id}/render/resume` queues every failed, cancelled, or interrupted task of the chain again and releases their pinned accounts. A scene interrupted by a restart may already exist on Muse, so resuming it requires `{"confirmDuplicate": true}` (409 `confirm_required` otherwise). Retrying or cancelling a single render task through `/api/tasks/{id}/...` has the same effect on the project.

The project status follows the chain: `completed` when every task succeeded, `cancelling` while a cancelled task is still running, `rendering` while one runs, `failed` after a failed or interrupted task, `cancelled` after a cancel. A scene request is sent to Muse once per attempt and is never resent automatically; a timeout or refusal fails the task and waits for the user. Task error codes added by rendering: `quota_exhausted`, `generation_timeout`, `generation_refused`, `media_download_failed`, `scene_missing`, `ffmpeg_unavailable`, `merge_failed`.

`POST /api/projects/{project_id}/render/restart` with `{"fromScene": n}` renders scene n and every later scene again, then merges again. It needs a finished or stopped render and a clip for every scene before n (409 `render_not_restartable` otherwise). The replaced clips and the merged video are deleted.

Scene prompts carry the scene's own prompt, the shared visual style and characters, the project's `look`, and quality requirements. With `continuity` other than `off`, the last frame of the previous scene is attached to the message (extracted with FFmpeg, so FFmpeg is then needed before scene 2 is sent): `reference` asks Muse to match it, `seamless` to start on it. If the frame cannot be read or attached the scene fails with `reference_frame_failed` or `reference_upload_failed` before anything is sent.

A scene's narration is sent as its voice-over, and a project `language` other than `auto` is stated for everything spoken.

The script and all scenes of a project are sent to one Muse conversation on one account, so the agent keeps the film's context: a script written by Muse opens the conversation and the render continues it on the same account. A new conversation is started after `MUSE_THREAD_SCENE_LIMIT` scenes (default 12), when the render moves to another account (only after a failure that points at the account), when the saved conversation can no longer be opened, and for every "render again".

`GET /api/projects/{project_id}/scenes/{number}/thumbnail` and `GET /api/projects/{project_id}/cover` serve JPEG stills (made with FFmpeg when a scene is rendered, or on first request for older clips; 404 `media_not_found` when FFmpeg is unavailable).

`GET /api/projects/{project_id}/scenes/{number}/video` and `GET /api/projects/{project_id}/video` serve a scene clip and the merged video (HTTP range requests supported); `?download=true` adds a download filename. Missing media returns 404 `media_not_found`. Deleting a project removes its media folder and cancels its waiting render tasks.

## Deleting a task

`DELETE /api/tasks/{task_id}` removes a finished task from the list for good and returns 204. Files the task made stay where they are (the library, the project), and nothing changes on Muse. It is refused with 409 `task_not_deletable` while the task is queued or running, while a queued or running task depends on it, and for a render task (`render_scene`, `merge_video`) of a project that still exists: those are the film's own record and are queued again to re-render or re-merge it, so they go only when the project is deleted. 404 `task_not_found` when there is no such task.

Every task in `GET /api/tasks`, `GET /api/tasks/{task_id}` and the other task responses carries `deletable`: whether the rule above lets it go (a waiting dependent is only checked by the request itself).

Reference files sent to Muse (a project's reference material, the frame of the previous scene, a Quick Create reference image) are attached to the message only once the Muse composer displays them; if it never does, the task fails with `reference_upload_failed` and nothing is sent.

## Settings and system status

`GET /api/settings` returns what the user may change in the app: `{"projectDefaults": {"durationSeconds", "aspectRatio", "language", "look", "continuity"}, "publicUrl": string | null}`. Until something is saved these are `60`, `16:9`, `auto`, `auto`, `reference` and `null`.

`PATCH /api/settings` changes the parts it is given and returns all of them. `projectDefaults` is always sent whole and follows the same rules as a project (duration 10-3,600 in steps of 5, a supported aspect ratio, language, look and continuity). `publicUrl` is an `http`/`https` address with a host, optionally a port and a path, at most 200 characters, without credentials, query or fragment; a trailing slash is dropped, and `null` or an empty string clears it. Anything else is 422 and nothing is saved.

- `POST /api/projects` takes `durationSeconds`, `aspectRatio`, `language`, `look` and `continuity` from `projectDefaults` for each of those fields the request leaves out.
- The public API builds result URLs from `publicUrl` when it is set; otherwise from the host a proxy forwards (`X-Forwarded-Host`, `X-Forwarded-Proto`), otherwise from the request's own address.

`GET /api/system` is read-only and describes what the server runs with: `version`, `dataDir`, `databaseRevision`, `ffmpeg` (`path` or null, `version`, `captions`: whether it can draw captions and titles), `browserPath` (the Chromium used for Muse, or null), `storage` (`databaseBytes`, `projectsBytes`, `libraryBytes`, `freeBytes`) and `limits` (`taskWorkers`, `browserSlots`, `planningTimeout`, `renderTimeout`, `threadSceneLimit`, `sessionRefreshMinutes`, `sessionRefreshWake`), which come from the `MUSE_...` environment variables read at start-up.
